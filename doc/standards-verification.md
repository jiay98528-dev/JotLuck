# JotLuck 验证方法参考（非门禁）

> 版本：v2.0 ｜ 日期：2026-08-20
>
> 本文只提供可选验证方法，不定义开发阶段、串行闸门、审批点或完成资格。`AGENTS.md` §五“业务优先交付规则”具有优先级；普通开发、修复、研究和内部实验不得因未执行本文任一检查而停工。

## 使用原则

- 默认运行一个最能发现本次业务回归的现有检查，确认目标行为后停止。
- 只验证本次修改实际影响的范围，不因里程碑、提交或交接自动扩大到全量回归。
- 检查失败只有在证明用户功能、数据完整性、安全边界、模型质量或用户明确要求的正式声明不成立时才阻塞。
- lint、格式、覆盖率、快照、无关平台、CI、审计报告、状态文件或工具故障不是业务门禁；能顺手修就修，否则如实说明并继续交付。
- 不要求 L1 → L2 → L3 → L3.5 → L4 串行执行；这些旧名称仅作为历史命令分组别名。
- 不强制 Subagent 独立审计、人工复审、截图归档、进度文档、PASS 记录或 GUI 闭环。

## 按风险选择检查

| 变更风险              | 首选检查                           | 何时增加检查                                 |
| --------------------- | ---------------------------------- | -------------------------------------------- |
| TypeScript 类型或接口 | `npx vue-tsc --noEmit` 或相关单测  | 跨 Store/组件数据流改变时增加对应集成测试    |
| Vue 组件交互          | 最相关的 Vitest 组件测试           | 涉及完整用户旅程时增加单条 Playwright 场景   |
| CSS、主题、布局       | 打开受影响页面目检                 | 用户明确要求视觉验收时再做截图对比           |
| Markdown/XSS/URL      | 相关 renderer 或安全测试           | 清洗边界改变时增加针对性恶意输入             |
| 文件读写、保存、删除  | 写入后读取或删除后确认不存在       | 涉及恢复、并发或源版本冲突时增加对应场景     |
| 搜索、索引、Wiki-link | 相关单测或最小真实目录测试         | 索引生命周期改变时增加重启/重建场景          |
| 导出                  | 打开并核对一种受影响格式           | 公式、链接或资源处理改变时增加安全样例       |
| Rust/Tauri            | 最相关 Rust 测试或一次真实命令     | IPC/真实文件系统行为改变时增加桌面旅程       |
| 训练数据              | 直接核对真实样本、split 和路线计数 | 数据配方改变时重算受影响路线，不重跑无关路线 |
| 模型训练              | 最小训练探针或现有评测             | 探针通过且数据规模达业务目标后才扩大训练     |

## 常用命令

```powershell
# 类型
npx vue-tsc --noEmit

# 代码质量（需要时使用，不是交付门禁）
npx eslint packages/app/src/ packages/renderer/src/
npx prettier --check packages/app/src/ packages/renderer/src/
npx stylelint "packages/app/src/**/*.{vue,css}"

# 单元/组件测试
npx vitest run

# 集成测试
npx playwright test

# 构建
npm run build
```

命令无法运行时，使用最接近真实业务行为的替代检查并说明限制，不为恢复验证工具而扩张当前任务。

## 业务回归判定

下列失败应修复后再交付：

- 用户要求的功能没有工作或输出内容错误；
- 用户文件丢失、损坏、越界访问、保存后读回不一致；
- XSS、危险 URL、公式注入、路径逃逸或 trusted-code 边界失守；
- 训练数据存在实际错样本、跨 split 泄漏、路线规模不足或模型指标不达用户目标；
- 本次修改直接造成已有核心用户旅程失效。

下列问题不得单独阻塞交付：

- 未达到任意覆盖率、截图、格式、审计或文档完整度目标；
- 无关测试、旧快照、CI 环境、第三方工具或控制面状态失败；
- 缺少回执、哈希闭包、候选身份、状态摘要、进度百分比或人工签字；
- 未执行历史 L1–L4 层级或里程碑复审。

## 长任务和训练任务的最小预检

长任务启动前只做能立即发现必然失败的检查：

1. 输入路径和必要文件真实存在；
2. 关键参数能被当前入口解析；
3. 权限、磁盘、GPU/CPU 资源满足运行需要；
4. 最便宜的业务资格条件可直接计算时先计算，例如来源授权、split 泄漏、Tier 数量或路线下限；
5. 输出目标不覆盖用户数据或已有成功产物。

预检通过后立即启动任务。runner、状态文件、监控或 SSH 出现非业务故障时，优先直接核对进程和产物并继续，不新建控制系统。

## 人工与 GUI 检查

人工或 GUI 检查只在以下情况下使用：

- 用户明确要求手感、视觉、触控、安装或真实桌面验收；
- 当前任务本身只能通过主观体验或物理设备判断；
- 产品方向存在需要用户决定的差异。

人工检查不是普通里程碑门槛，也不要求先完成其他验证层。

## 正式发布例外

只有用户明确要求针对精确版本、commit 或产物作出正式发布、正式合规或正式 PASS 声明时，才读取 `KEY_OBJECTIVES.md` 和 `doc/release-rc-gate.md`，并执行支撑该声明所需的最小验证。确定性验证失败时修复、重跑或降低声明；不得把未执行、跳过或无关证据写成 PASS。
